1.1. Восстановление данных в полном объёме за предыдущий день

Для решения задачи подходит полное резервное копирование (Full Backup). Необходимо настроить ежедневное создание полной резервной копии базы данных с хранением копий на отдельном сервере или в облачном хранилище. При возникновении сбоя можно восстановить базу данных из последней резервной копии. Недостатком данного подхода является потеря изменений, внесённых после создания копии.

1.2. Восстановление данных за час до предполагаемой поломки

Для этой задачи подходит Point-in-Time Recovery (PITR) — восстановление базы данных на определённый момент времени. Для этого необходимо регулярно создавать базовые резервные копии и настроить непрерывное архивирование журналов транзакций WAL. При восстановлении базовая копия дополняется журналами WAL до требуемого момента времени. Это позволяет восстановить базу данных практически на любое состояние в пределах срока хранения журналов.

1.3. Моментальное переключение на работающую базу данных

Да, такой сценарий возможен. Для этого необходимо организовать кластер высокой доступности (High Availability) с использованием репликации баз данных и автоматического переключения (Automatic Failover).

В такой конфигурации имеется основной сервер (Primary) и один или несколько резервных серверов (Standby / Replica). Данные реплицируются с основного сервера на резервные. При отказе основного сервера система обнаруживает проблему и автоматически переключает работу на одну из доступных реплик, которая становится новым основным сервером.

Для минимизации потери данных можно использовать синхронную репликацию. При этом важно учитывать, что она может увеличивать задержки записи и зависеть от доступности реплики.

Заключение:

Для финансовой компании рекомендуется использовать комплексный подход:

Ежедневное полное резервное копирование.

Непрерывное архивирование WAL-журналов и возможность PITR.

Кластер высокой доступности с репликацией и автоматическим Failover.

Хранение резервных копий отдельно от основной инфраструктуры.

Резервное копирование обеспечивает возможность восстановления данных, а репликация и автоматическое переключение позволяют минимизировать простой информационной системы. Эти механизмы дополняют друг друга и должны использоваться совместно.

2.1. Резервное копирование и восстановление базы данных
В PostgreSQL для этих задач используются две утилиты:
- pg_dump — создание резервной копии базы данных.
- pg_restore — восстановление базы данных из резервной копии в архивном формате.
Для резервного копирования удобно использовать формат custom (-Fc). Он поддерживает сжатие, выборочное восстановление отдельных объектов и параллельное восстановление.
PostgreSQL+1


Пример резервного копирования:
pg_dump -h HOST \
  -p 6432 \
  -U pguser \
  -d netology \
  -Fc \
  -f netology_backup.dump


Здесь:
- -h — адрес сервера PostgreSQL;
- -p — порт подключения;
- -U — пользователь базы данных;
- -d — имя базы данных;
- -Fc — архивный формат custom;
- -f — имя файла резервной копии.
Пример восстановления:

Сначала необходимо создать пустую базу данных:
createdb -h HOST -p 6432 -U pguser netology_restore


Затем восстановить данные:
pg_restore -h HOST \
  -p 6432 \
  -U pguser \
  -d netology_restore \
  netology_backup.dump


После восстановления можно подключиться к базе и проверить наличие таблиц и данных.

Официальная документация PostgreSQL:
- pg_dump — резервное копирование
- pg_restore — восстановление
2.1*. Автоматизация резервного копирования
Автоматизировать процесс можно с помощью планировщика задач Linux cron.

Например, можно настроить ежедневное резервное копирование базы данных в 02:00.

Для этого создаётся Bash-скрипт, который:
1. Формирует имя резервной копии с текущей датой.
2. Запускает pg_dump.
3. Сохраняет архив в отдельный каталог.
4. Проверяет результат выполнения.
5. Удаляет старые резервные копии, например старше 30 дней.
Пример задания в crontab:
0 2 * * * /usr/local/bin/backup_postgres.sh


Таким образом, резервное копирование будет выполняться ежедневно автоматически, без участия администратора.

Дополнительно рекомендуется:
- хранить резервные копии на отдельном сервере или в облачном объектном хранилище;
- ограничить доступ к резервным копиям;
- настроить уведомления об ошибках резервирования;
- периодически проверять возможность восстановления базы данных из резервной копии.

3.1. Пример инкрементного резервного копирования
В MySQL существует несколько способов инкрементного резервирования.

Для MySQL Community Edition можно использовать механизм бинарных журналов (Binary Log).

Принцип работы:
1. Сначала создаётся полная резервная копия базы данных.
2. MySQL записывает все последующие изменения в бинарные журналы.
3. Периодически выполняется ротация журналов командой FLUSH LOGS.
4. Закрытые файлы binlog копируются в отдельное хранилище.
5. При восстановлении сначала загружается полная копия, затем последовательно применяются бинарные журналы.
Пример команд:

Проверяем, включено ли ведение бинарных журналов:
SHOW VARIABLES LIKE 'log_bin';


В MySQL 8.0 эта функция включена по умолчанию.

Выполняем ротацию бинарных журналов:
FLUSH LOGS;


Смотрим список журналов:
SHOW BINARY LOGS;


Копируем закрытые файлы бинарных журналов в отдельное хранилище:
cp /var/lib/mysql/binlog.000001 /backup/mysql/


Имя файла здесь условное. Необходимо копировать все журналы, содержащие изменения после последней полной или инкрементной копии, не пропуская последовательность файлов.

При восстановлении сначала загружается полная резервная копия, а затем применяются бинарные журналы:
mysqlbinlog /backup/mysql/binlog.000001 \
            /backup/mysql/binlog.000002 | mysql -u root -p


Таким образом, можно восстановить базу данных до определённого момента времени, применив все изменения, записанные в бинарных журналах.
MySQL+2


Альтернативный вариант — MySQL Enterprise Backup.

В коммерческой редакции MySQL Enterprise Edition имеется специальная утилита mysqlbackup, которая поддерживает физическое инкрементное резервирование.

Пример команды из официальной документации:
mysqlbackup --defaults-file=/home/dbadmin/my.cnf \
  --incremental \
  --incremental-base=history:last_backup \
  --backup-dir=/backup/temp \
  --backup-image=incremental_image.bi \
  backup-to-image


Этот вариант создаёт инкрементную копию на основании предыдущей успешной резервной копии.

3.1*. Преимущества использования реплики перед обычным резервным копированием
Использование реплики (Replica) имеет несколько преимуществ:

1. Снижение нагрузки на основной сервер. Резервное копирование можно выполнять на реплике, не создавая дополнительную нагрузку на Master. Это особенно важно для высоконагруженных баз данных.

2. Повышение доступности системы. Если основной сервер выходит из строя, реплику можно использовать для переключения рабочих приложений.

3. Возможность выполнять обслуживание. На реплике можно проводить резервное копирование, проверку данных и некоторые административные операции, не затрагивая основной сервер.

4. Дополнительная копия данных. Реплика содержит данные, получаемые от основного сервера, поэтому позволяет быстрее получить доступ к актуальной информации при отказе Master.

Однако важно учитывать, что репликация не заменяет резервное копирование. Если на основном сервере произойдёт ошибочное удаление данных или логическое повреждение базы, эти изменения могут автоматически попасть и на реплику.

Поэтому рекомендуется использовать оба механизма одновременно: репликацию для обеспечения высокой доступности, а резервное копирование — для восстановления данных после ошибок и сбоев.
